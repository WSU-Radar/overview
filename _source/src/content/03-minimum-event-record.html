• The Minimum Event Record (MER) is a small, standard set of fields that describes one public-health event and the times it passed through detection, notification, investigation and response.
  • It is a data standard and exchange profile — not a new database, not a new user interface.
  • Systems publish a few fields about an event and subscribe to what others published; each stays authoritative for its own data.
  • For the first time, one event has one identity across human, animal, laboratory and response systems — which is what makes 7-1-7 measurable.

Everything else in RADAR keys off the MER: analytics link signals to it, DMT-PHE classifies it, GHEC-AI responds to it, and MEL measures time along it. If the MER is wrong or bloated, every downstream piece inherits the problem. It is also the first MVP component and must be agreed with KNPHI and in operational use for Gate 1.

What the MER is

When a suspected outbreak occurs today, the facts about that single event are scattered: the community signal in m-Dharura, the animal signal in KABS, the case count in KHIS2, the lab result in a laboratory system, and the decision in an EOC spreadsheet. No system holds a record of the event itself. Proposal

The MER fixes this with the smallest possible shared record: an event identity, a handful of descriptive fields, a set of lifecycle timestamps, and pointers back to the source records. It is the “bridge” that achieves systems integration before the heavy infrastructure needed for full integration exists.

Design rules

These rules keep the MER small, safe and durable. Recommended

Minimum necessary

Only fields needed to identify, classify, time and link an event. Anything else stays at the source.

No direct identifiers

No names, phone numbers or national IDs. Counts and places, not people.

Pointers, not copies

Linked records are referenced by source system and source ID.

Everything attributed

Every field change records who or what changed it, when, and from which source.

Stable identity

The event ID never changes, even when the suspected disease does.

Disease-agnostic

Hazard is a coded field, so new threats need a code, not a schema change.

Lifecycle

  • Who can open an MER? RADAR opens one automatically when a new signal does not match an existing event; an officer can also open one manually (e.g. a phone report).
  • Merge and split. If two MERs turn out to be the same event, they merge — the surviving mer_id keeps both histories and the other becomes an alias. A split creates a new MER and moves selected links. Both actions require a human and are audited.
  • Discarded is a state, not a deletion. False alarms are evidence: they are needed to measure positive predictive value and alert burden.

Timestamps and the 7-1-7 clock

The 7-1-7 target expects every outbreak to be detected within 7 days of emergence, notified within 1 day of detection, and to have seven early response actions completed within 7 days of notification. Research The MER uses the 7-1-7 Alliance definitions so results are comparable internationally:

  • Detection: the date the event is first recorded by any source or in any system.
  • Notification: the date the information reaches the first public-health authority responsible for action.
  • Early response completion: the last completion date across the seven actions; an action that does not apply is recorded as “N/A”, not left blank.
Rules for messy time data
  • Store the original source timestamp and the time RADAR received it separately — they answer different questions.
  • Back-entered data (e.g. after a system outage) keeps its real event time and carries a “back-entered” flag.
  • Unknown is null; not applicable is N/A. Never default a missing time to “now”.
  • Store all times in UTC with the source time zone; display in East Africa Time (UTC+3).

Linking signals to events

Linking is the hardest and most consequential step. A wrong merge hides an outbreak; a missed link splits one. RADAR applies three passes in order and records which one made each link. Recommended

  1. Shared identifiers. If two records share a reliable ID (for example a lab specimen ID quoted in an EBS follow-up), link them deterministically.
  2. Rules. Same or adjacent administrative unit, overlapping time window and compatible hazard/syndrome (configurable per disease — e.g. a wider window for RVF than for cholera).
  3. Probabilistic matching. A Fellegi–Sunter model (e.g. the open-source Splink library) scores candidate pairs. High scores link automatically; borderline scores go to a data steward's review queue.

Exchange model: publish and subscribe

Each participating system publishes a small number of standard fields about an event and subscribes to what others have published about the same event. Existing systems keep operating exactly as they do now. Proposal In the MVP, “publishing” will mostly be done on behalf of source systems by RADAR's connectors (integration levels 1–2); native publishing by source systems is the Level 4 end state (doc 05).

Governance of the standard

  • Owner: KNPHI. The MER must be agreed and in operational use by Gate 1 and published and adopted as a KNPHI standard by Gate 2. Proposal
  • Versioning: semantic versions (v0.x during the MVP, v1.0 at adoption). Additive changes are minor versions; removing or redefining a field is a major version with a migration plan.
  • Change control: proposals go to the Technical Working Group; KNPHI approves (doc 15).
  • Code lists: hazards, statuses, link methods and action types are published as FHIR CodeSystems/ValueSets and versioned with the profile.

Open questions

  1. Which hazard code list is authoritative? IDSR priority list, DMT-PHE trigger cards and ICD-11 overlap but differ. Owner: KNPHI · MER workshop
  2. Do counts live in the MER or only at the source? Counts make the MER more useful but harder to keep consistent. Owner: TWG
  3. Finest geography allowed? Ward level helps clustering; it may raise re-identification risk in sparse areas. Owner: Data governance group
  4. Who may merge or split events? Suggest data stewards at KNPHI and county EOC managers. Owner: KNPHI
