• RADAR speaks FHIR R4 for system-to-system exchange, built on DHA's Kenya Core implementation guide, and MCP for connecting the AI agent to tools.
  • Every source uses the same seven-step connector pipeline; raw data is kept so it can be re-processed.
  • Sources climb an integration maturity ladder (L0 manual → L4 publish/subscribe). The MVP only needs L1–L2.
  • Anything already on LATTICE goes through LATTICE.

“Integrate everything at once” is a challenge: too many systems, standards and business rules, high infrastructure and maintenance costs, and a brittle result that is hard to sustain. Proposal A single repeatable connector pattern, open standards, and a ladder that lets each source start simple is how RADAR stays incremental and sustainable — and how a new stream can be added later as a configuration change rather than a rebuild.

Principles

Federated

Sources remain the system of record. RADAR holds identities, timestamps and pointers.

Standards first

Reuse Kenya Core, national code lists and existing IGs before inventing anything.

Minimum necessary

Pull only the fields RADAR uses, at the coarsest granularity that works.

Start low, climb

Begin at the integration level a partner can support today.

Resources can be checked locally with the HL7 FHIR validator against the IG packages; DHA runs a separate certification assessment in which interoperability is one domain — passing validation is not the same as being certified. Integration maturity ladder

The ladder makes “integration” concrete and measurable. It also feeds the Gate 2 threshold of ≥ 80% dataset integration from baseline: “integrated” should be defined as Level 2 or higher with automated, monitored flows. Recommended

FHIR and MCP: different jobs

The proposal names both FHIR R4 and the Model Context Protocol (MCP) as RADAR's open integration protocols. Proposal They are complementary:

  • FHIR moves records between systems under contracts that validators can check.
  • MCP gives the AI agent a controlled set of tools — look up an MER, fetch a trigger card, search guidelines, request a GHEC-AI hand-off.

MCP design rules

  • Target the current specification (2026-07-28). It makes the protocol stateless (no session handshake), adds Mcp-Method/Mcp-Name headers so gateways can route and authorise without parsing bodies, moves server-initiated requests to multi-round-trip requests, and tightens OAuth (issuer validation per RFC 9207; Client ID Metadata Documents instead of dynamic registration). Roots, Sampling and Logging are deprecated. Research
  • Read-only by default. Tools that write or send anything outside RADAR (e.g. GHEC-AI hand-off) only execute after a named officer approves the action in the DMT-PHE workspace.
  • Narrow, typed tools. Each tool has a strict input/output schema and returns only minimum-necessary fields.
  • Everything logged. Each tool call (who, what, parameters, result size) goes to the audit log.
  • Route through the gateway so the same authentication, rate limits and audit apply as for FHIR traffic.

The GHEC-AI interface

GHEC-AI (Sobek) is the downstream response-matching layer: it matches approved response needs to available workforce and capacity. Only minimum-necessary operational information passes, through secure API/MCP interfaces, and only after authorised escalation. Proposal Initial interface specifications, agreed jointly with Sobek, are an MVP component.

Data quality management

  • Four dimensions tracked per source per week: completeness, timeliness (lag from event to arrival), validity (passes checks), uniqueness (duplicates).
  • Data stewards at KNPHI own each source's quarantine queue and the relationship with its custodian.
  • Feedback to sources: recurring problems go back to the custodian — RADAR should improve source data over time, not silently patch it.

Testing interoperability

  • Contract tests per connector using captured, de-identified sample payloads.
  • A synthetic data generator that can replay realistic outbreaks (RVF, cholera) end-to-end in development.
  • FHIR validation against Kenya Core and the MER profiles on every build.
  • Staging replays of de-identified real feeds before any connector goes to production.
